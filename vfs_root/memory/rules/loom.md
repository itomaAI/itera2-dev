# Loom 運用手順（AI 側）

対象: `data/apps/loom/*.md` ／ アプリ: `apps/loom.html`

**記法の正は `docs/manual/loom_notation.md`。利用者向けの使い方は `docs/manual/loom.md`。**
ここには**私（AI）の動き方だけ**を書く。記法をここに写さない（二重管理になり、片方が黙って腐る）。

Loom は**利用者と私が一緒に長い仕事を進めるための板**である。
器は 2 つ —— **プロジェクト**（意図＝観点。終わらない。知識の置き場）と
**タスク**（依頼＝完了条件。終わる。仕事の置き場）。
操作は 3 つ —— **置く・畳む・移す**。詳しくは記法を読む。

---

## 0. 着手の前に読む（この順。飛ばさない）

1. **この文書**
2. **札の本文を全部**（`## 依頼` だけで済ませない）
3. **所属プロジェクトの `## 意図` `## 文脈` `## 履歴`**。`parent:` を根まで遡る
   * **タスクは文脈を持たない。** 知識は所属プロジェクトの `## 文脈` にある。
     ここを読まずに始めると、そのタスクは「世界にこの依頼しか無い」状態で走る
   * **`## 履歴` だけでは足りない。** 源が知っていることは、その源の `## 文脈` にも入っている
4. 記法で迷ったら `docs/manual/loom_notation.md`（§7 に判別表がある）

**読む費用は、見切り発車の費用より安い。** 迷ったら読む側に倒す。

## 1. まず拾う（セッション開始時・依頼通知を受けたとき）

```
<search query="^status: (todo|doing)" path="data/apps/loom" regex="true" context="0" />
```

**行頭に固定する（`regex="true"`）。** 素の `status: doing` で検索すると、
**本文でその文字列に言及しただけの札**に当たる。front matter は札に 1 行しか無いので、行頭固定なら誤検出しない。

板の全景が要るときは `<search query="^status: " path="data/apps/loom" regex="true" limit="30" />` で 1 手で出る。

**板そのものを疑うときは、アプリの「全景」を見る。**
枚数・状態の分布・根と子孫の数のほかに、**ファイルの数と画面に出ている札の数の照合**が出る。
読めなかったファイル・画面に出ない札・id の重複・親が板に無い札が見つかったときだけ赤い帯が出るので、
**何も出ていなければ板は健全**である。`inject_js` から `censusOf(nodes)` / `unreachable()` を直接呼んでもよい。

* `todo` / `doing` が**私のボール**。`inbox` / `blocked` / `review` / `paused` は
  利用者のボールなので触らない
* 「今日やる」は `scheduled: YYYY-MM-DD` が今日以前のもの
* **拾うのはタスク（`T-*`）だけ。** プロジェクト（`P-*`）は手番を持たない
* **アプリは起動しなくてよい。ファイルが唯一の正**

## 2. 動かし方（タスク）

| 場面 | やること |
| :-- | :-- |
| 着手する | **先に `## 計画` に分解を書く**。そのうえで `status: todo` → `doing`。分解は進捗管理であると同時に、**依頼をどう解釈したかの提示**である |
| 決めた | **その場で**レポートの枠に 1 行足す（`## 進捗` の中の `### レポート`）。あとでまとめて書こうとすると必ず落ちる。**却下枠を省略しない** |
| 分かった | `## 進捗` に「何が分かって、次に何をするか」 |
| 答えが要る | `## 確認事項` に書き、`status` を `blocked` にし、**チャットでも言う**（§5） |
| 増えたのが**仕事** | **分解**（子タスク） |
| 増えたのが**知識・観点** | **分岐**（子プロジェクト）。ただし**意図を書くのは利用者**なので、切ってよいか一言確認する |
| 総括が二度要ると感じた | **それはタスクではない。** プロジェクトにすべきだった合図 |
| 中断を指示された | 新しい作業を始めない。次の一手を `## 進捗` に書いて止まる。状態は既に `paused`。自分で戻さない |
| 終わった | `## 成果物` にパスを書き、`## 進捗` の中に `### レポート` を書く。**そこで止める。手で転記しない** |
| 閉じる（＝確認へ回す） | アプリの「**確認へ回す ✓**」は、レポートがあることを確かめて **`review`（確認待ち）にするだけ**。**ここでは親へ運ばない**。**手で転記しない** |
| 運ばれるのはいつか | **`done` になった瞬間** —— 利用者が「確認したので完了にする」を押したとき。**確認で分かったことを親へ載せるため**にこの順にしてある。運ぶのはちょうど一度だけ（親の履歴に残る `完了: <id>` を証拠に見ている） |
| だから私は | **`done` にしない。** `review` で止める。`done` は利用者の一手であり、**転記の引き金**でもある |
| 自律で閉じるなら | `inject_js` で **`await window.complete('T-XXXX')`** —— **id を渡す**。id を省くと**画面で選択中の札**に作用するので、渡さないと別の札を閉じうる |
| その戻り値を見る | `{ ok, id, reports, artifacts, empty, delivered, reason }` を返す。**`ok` を確かめる。** **id 指定でレポートが無いときは、回さずに `ok:false, empty:true` を返す**（ダイアログは出さない —— 利用者の画面に確認を出して応答を待つと、こちら側は応答が来るまで止まる）。空でも回したいときだけ `complete('T-XXXX', { force: true })` |
| 画面のボタンは | レポートを書いてあれば確認ダイアログは出ない。書いていなければ利用者に訊く（人が居る前提の経路なので、ここだけは対話でよい） |
| レポートに追記したい | `## 進捗` に `- 日時 …` の形で書くと**枠の外に落ちて運ばれない**。枠の中へ足すにはアプリの「**レポートに追記**」ボタンを使う。書式は **`- **追記 <日時> 名前**: 本文`**（先頭が `- **` なので枠が閉じない）。**私が自分で書き足すときも同じ書式にする** |
| 中止 | **親に載せずにタスクを終わらせる**道。中止では運ばない |

* **子タスクの成果をプロジェクトへ直接上げない。** 親タスクのレポートで畳まれて上がる（履歴の粒度のつまみ）
* **子が全部閉じても親タスクは閉じない。** 統合の一手が残る。親を閉じるとき開いている子は**プロジェクト直下へ繰り上げる**

## 3. 畳む／移す（いちばん間違えやすいところ）

* **畳むのは私の仕事。** アプリのボタンは依頼を送るだけで、機械が要約文を作ることはない
* **移すときは畳まない。** 転記は、子が書いた総括を**そのまま**親の履歴へ載せる。
  親の観点で子を畳むことはできないから。**親が読みにくければ、親自身の観点で畳む**（＝文脈生成）
* **自分が書いた総括だけを上げる。** 運ばれてきた総括には出どころが付いている（`### 総括 <日時>（P-0002）`）。
  これを自分の総括として数え直すと、**根に子孫全部の総括が積み上がる**
* **渡した側は「どこまで渡したか」を書く**（`… まで／N 件`）。**総括の時間軸どうしで比べる**
* **畳んだものだけが古びる。** 古びの印は画面の `→ n`。取り込み点は `## 文脈` の最後の「… まで」から導く
* **追随は積むだけ**（書き換えない）。**再生成のときだけ `## 文脈` を丸ごと書き換えてよい**（写しだから）

## 4. 書き換えてよいもの・いけないもの

**書き換えてよいのは 3 つだけ** ——
front matter の値 ／ `## 成果物` の一覧 ／ `## 文脈`（写しなので畳み直してよい）。

* **`## 履歴` と `## 進捗` は絶対に書き換えない。** 唯一の正であり、腐りを検出できないため
* **履歴に残った古い題を直さない。** 表示のときに現在の題へ解決される
* `## 文脈` を再生成したら `## 履歴` に 1 行残す（`再生成: … を畳み直した（前版は … 生成）`）
* 欠けを後から埋めるときは、**埋めたと分かる形で足す**（既存の行は書き換えない）

## 5. 通知の穴（設計上の制限）

* **私 → 利用者 の通知経路が無い。** 利用者 → 私 は届くが、逆は無い。
  板を `blocked` にしても、アプリを開かなければ気づかれない。
  → **質問を立てたら、チャットでも一言伝える。板に書いただけで待たない**

## 6. 札を編集するときの作法

* **追記は必ず日時から始める。** `- YYYY-MM-DD HH:MM 名前: 本文`。
  **時刻は `<get_time />` で取る。推測で書かない。**
  これは作法ではない —— 出来事の枠は「次の日時つきの行」で閉じるので、**日時が無いと枠が閉じない**
* **日時を付けるのは `## 進捗` / `## 追加要望` / `## 確認事項` だけ。**
  `## 計画` は日時を前置すると**チェックボックスにならない**。`## 成果物` は一覧なので日時が入ると読めなくなる
* **見出しは変えない。** アプリはこの見出しを目印に追記先を見つける
* **同じファイルは 1 ターンに 1 編集。**（札に限らない。ソースでも同じ）
  1 ターンに出した道具は**並行して走る**ので、同じファイルへ編集を複数出すと互いの書き込みを踏み、
  **全部が成功を返したうえで、一部の変更だけが消える**。
  複数箇所を直すならターンを分けるか、全文の書き直しで 1 回にまとめる
* **書いたら読み直し、本文で入ったことを確かめる。** 成功の表示は、入った証拠ではない
* front matter は `status: doing` のように**キーごと**置換する（キーは front matter 内で一意）
* **利用者が札を編集している間、私の追記は画面に反映されない**（保存が中止され掲示が出る）。
  データは消えないが、**開いていると分かっているときは追記を後回しにする**

## 7. アプリ無しで札を起こす

**新しい id** … `<search query="^id: T-" path="data/apps/loom" regex="true" limit="100" />` の最大値 +1
（プロジェクトは `^id: P-`）。**空いた番号を再利用しない** —— 履歴に残る古い参照が、
別の札の題で表示されてしまう。

1. `data/apps/loom/T-XXXX.md` を作る。front matter は `id/kind/title/status/priority/created/parent/refs`、
   本文は 6 つの節（`## 依頼` `## 計画` `## 追加要望` `## 進捗` `## 確認事項` `## 成果物`）
2. **親の履歴に出来事を 1 行足す** —— `- 日時 起票: T-XXXX「題」`（親タスクの下なら `分解:` で `## 進捗` へ）
3. **辺の正は子の front matter の `parent:` 1 箇所だけ。** 親の履歴に入る行は辺の複製ではなく出来事の記録

**`T→P` の辺は無い。** タスクの下にプロジェクトは吊るせない（タスクは通り道であって親にならない）。
