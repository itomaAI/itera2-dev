# Local Bridge — ローカル機を Itera から扱う

最終更新: 2026-08-22 / サーバー v3.5.0 / デーモン v3.7

VFS の一部を、ホスト機（あなたの PC や GPU サーバー）の実ディレクトリに繋ぐ仕組み。
**ファイル同期だけでなく、シェル実行・検索・実体化／スタブ化まで含む**。

## 構成

| 部品 | 実体 | 役割 |
| :-- | :-- | :-- |
| ホスト側サーバー | `services/itera_bridge_server.py` | 1ファイルでサーバーと CLI を兼ねる。複数ルートを扱う |
| OS 側デーモン | `services/local_bridge.html`（pid `local_bridge`） | マウント・調停・LPML ツールの提供 |
| 設定アプリ | `apps/local_bridge_settings.html` | 接続とルートの一覧・操作・配布 |
| 接続設定 | `system/config/local_bridge.json` | 接続一覧と無視パターン |
| アンカー | `data/apps/local_bridge/anchors/` | 前回同期した状態と**相手の同一性** |

マウント先は **`local/<接続名>/<ルート名>`**。

## 使いはじめ

ホスト側（Python 3・`fastapi` / `uvicorn`、任意で `watchdog`）:

```bash
python3 itera_bridge_server.py serve --port 8001      # 起動
python3 itera_bridge_server.py attach ~/projects/foo  # ルートを追加（起動後いつでも可）
python3 itera_bridge_server.py ls
python3 itera_bridge_server.py detach foo             # 取り外し
```

ルートは `~/.itera/roots.json` に永続化されるので、次回の起動時に復帰する。
ssh 越しの機械は `ssh -L 8002:localhost:8002 <host>` で転送し、設定アプリで
`http://127.0.0.1:8002` を追加する。**接続名は書かなくてよい**（サーバーが名乗る）。

## 接続名と同一性

**URL は相手が誰かの根拠にならない。** `ssh -L` を使うと、どの機械のサーバーも
OS からは `127.0.0.1:<port>` に見える。実際にこの環境の2台は
ユーザー名（`ryamauchi`）もホームのパスもそっくりだった。

そこでサーバーは `/api/status` で次を名乗る:

* `hostname` / `user` / `platform`
* `machineId` … `~/.itera/machine.json` に永続化した UUID

接続名は `hostname` から決まり、設定へ書き戻される（マウントパスが安定する）。
**同じ `machineId` を名乗る接続が2本あると警告する**（同じディレクトリを二重に
同期すると、互いの書き込みを削除と誤読して壊れるため）。

## 安全弁（何を守るために止まるか）

* **同一性の照合。** アンカーに「前回の相手（machineId ＋ ルートの実パス）」を記録し、
  食い違ったら**調停を中止して警告**する。同名ルートを別ディレクトリへ向け直したとき、
  古い残骸が新しいディレクトリへ送信されるのを防ぐ。
  意図した組み合わせなら、警告に出るアンカーを削除すれば再開する。
* **切断では消さない。** 一時的な切断（スリープ・回線断）で VFS 側にしか無い実体を
  失わないため。後始末は**意図的な `detach`** のときだけ行う。
* **detach の後始末。** 全件スタブなら削除。**実体が1件でもあれば削除せず**
  `local/<接続名>/<ルート名>.detached-<日付>` へ退避し、開けなくなるスタブだけ除く。
* **スタブ化（`local_release`）は確認が取れたときだけ。** ホストに実体があり
  ハッシュが一致することを確かめてから捨てる。確認できなければ中断する。

## LPML ツール（Itera 用）

| ツール | 用途 |
| :-- | :-- |
| `bash_exec` | シェル実行。`scope="host"` でルート外も可。`cwd` は毎回指定（永続化しない） |
| `local_search` | ホスト側の全文検索。**スタブのままでも中身を探せる** |
| `local_fetch` | スタブ → 実体（ダウンロード） |
| `local_release` | 実体 → スタブ（VFS の容量を空ける） |

実行モードは接続ごとに `ask`（都度確認）／`auto`（確認なし）。設定アプリで切り替える。

## すべてスタブに戻す（設定アプリ）

ルートの行の「すべてスタブに戻す」を押すと、そのルートの**実体をまとめてスタブに戻し、
VFS の容量を解放する**。実体はホスト側にあるので、開けば自動で取り直せる。

**捨てる前に、1 件ずつホストと照合する。**

| 状態 | どうなるか |
| :-- | :-- |
| ホストに同じ内容がある（ハッシュ一致） | スタブにする（VFS のバイト列を捨てる） |
| ホストに実体が無い | **見送る**（消さない） |
| 内容が食い違う | **見送る**（VFS 側の編集を失わない） |
| ホストに問い合わせられない | **中断する**（「無い」と読み替えない） |

* 判定は**デーモンにしかない**。設定アプリは依頼して結果を受け取るだけで、同じ判定を持たない。
  安全に関わる判定を 2 か所に置くと、片方だけ直って乖離するため。
  したがって**デーモンが動いていないとボタンは出ない**。
* 200 件ずつ確認する。ルート全体を 1 回で問い合わせると、ホストが全件のハッシュを
  計算し終えるまで何も返らず、進捗も出せない。
* 終わると「スタブ化 N 件 / 見送り M 件」と内訳が出る。**見送りは失敗ではない**。
  上の表のとおり、消してはいけないものを消さなかったということ。
* 同じことは `local_release` でもできる（こちらはパスを絞れる）。**実装は同じ関数を通る。**

## 無視するファイル（設定アプリ）

データセットのように**中身を VFS へ持ってくる気が無い木**は、スタブすら作らないほうがよい。
スタブは 1 バイトも実体を持たないが、**索引には 1 件として載る**。数万件になると索引そのものが重くなる
（実測 2026-08-21: スタブ 36,286 件で索引 30.4MB、アンカー 8.6MB）。

設定アプリの「無視するファイル」で、1 行に 1 つずつパターンを書く。

| 書く場所               | 効く範囲                 |
| :--------------------- | :----------------------- |
| すべての接続に効く既定 | 全接続・全ルート         |
| 接続ごと               | その接続のすべてのルート |
| ルートごと             | そのルートだけ           |

**三つは和で効く**（上書きではない）。接続ごとの設定で全体の既定を弱めることはできない。
緩めたいときは全体の既定から外す。

* `/` を含むパターンはルートからの相対パス全体に照合する（例: `output/tmp`）
* `/` を含まないパターンは**パスの各段**に照合する（例: `data` は途中の `data/` にも当たる）
* `*` と `?` が使える。`#` で始まる行は覚え書きとして無視される
* **設定はデーモンの起動時に読まれる。** 変更したら「デーモン再起動」を押す

### あとから足したパターンは、既にあるスタブには効かない

無視は走査の入口で読み飛ばすだけなので、**すでに作られたスタブは残る**。
そのためにルートごとの「無視対象のスタブを掃除」がある。

| 対象                     | どうなるか                                                                 |
| :----------------------- | :------------------------------------------------------------------------- |
| 無視に当たるスタブ       | VFS の索引から消す。アンカーからも落とす                                   |
| 無視に当たるディレクトリ | 中に残るものが無ければ消す                                                 |
| **実体化済みのファイル** | **消さない**（件数だけ知らせる。捨てたいなら「すべてスタブに戻す」を先に） |
| ホスト側のファイル       | **一切触らない**                                                           |

* 押す前に必ず件数を数え、確認の画面に出す。「対象を数える」だけを押すこともできる
* 数えるのも掃除するのも、**いま動いているデーモンの設定**で行う（保存しただけでは変わらない）
* パターンを外せば、次の走査でスタブとして戻る。**ホストに実体がある限り失われない**

## 落とし穴

* **サーバーの再起動を `bash_exec` の中で行わない。**
  シェルは**サーバーの子プロセス**なので、その中で親を kill すると結果を返す経路ごと消える。
  遅延 ＋ `setsid` で切り離すこと。プロセスの特定は
  `ss -tlnp | grep ':<port>'`（＝ポートの持ち主）で行う。コマンドラインの綴りは当てにならない。
* **スタブを削除／マウント外へ移動すると、実体化されたうえで移り、ホスト側の実ファイルは消える。**
  「コピー」ではなく「取り出し」。マウントの掃除は必ず
  `unregisterSyncProvider()` を先に呼んでから。
* **`file_info` / `list_files` ではスタブと実体を区別できない。**
  区別できるのは `MetaOS.fs.getSyncState()` だけで、判定は `syncState === 'stub'`。
  なお `getSyncState()` は `size` を返さない。
* 設定の変更は**デーモンを再起動すると反映される**（設定アプリのボタン）。
* **反映が遅いときは、まず監視が張れているかを見る。**
  `curl -s localhost:<port>/api/status` の各ルートの `watching` が `false` なら、
  変更検知は効いておらず**60秒ごとの保険走査だけ**で動いている（＝遅いが、止まってはいない）。
  理由は `watchError` に出る（watchdog 未導入、inotify の上限など）。
  v3.3.0 以前は `attach` で追加したルートが必ずこの状態だった。
* **反映の速さを測るとき、`bash_exec` の中で書き込んではいけない。**
  `/api/exec` は**コマンド終了時に全スキャナへ `touch()`** するため、監視ではなく
  その `touch` で気づいてしまい、計測にならない。書き込みを `setsid` で遅らせ、
  exec が終わったあとに起こすこと。

## 反映にかかる時間

**v3.5.0（現行。PR #29 で main に取り込み済み）**: ホストで書き込んでから VFS に映るまで
**約2秒**（1.97 / 2.30 / 2.09 / 2.35 / 2.04 秒）。
内訳は次のとおりで、**いまの支配項はホスト側の静穏待ち 1.5 秒**である。

**v3.4.0（旧）**: 約4〜6秒（実測 4.39 / 4.39 / 5.97）。下の表から long-poll の行を除き、
OS 側のポーリング **0〜5 秒**（平均 2.5 秒）とデバウンス 0.8 秒に置き換えたもの。
ばらつきが大きいのは、この 0〜5 秒があるためである。
**サーバーとデーモンは版が違っても動く**（下の「互換」を見よ）。

| 段 | 時間 | 何のための待ちか |
| :-- | :-- | :-- |
| ホスト側の静穏待ち | 1.5 秒 | 連続イベントをまとめる。**巨大な木の移動でハングした事故（v2.0）を受けた保険**。安易に縮めない |
| 走査ループの刻み | 0〜0.5 秒 | `scan_loop` の `time.sleep(0.5)` |
| long-poll の刻み | 0.1 秒 | サーバーが版の変化を見に行く間隔 |
| OS 側デバウンス | 0.15 秒 | ホスト由来の調停。VFS 側の書き込み直後だけ 0.8 秒に戻る |
| 突き合わせ | 0.17 秒 | 1,718 項目。うち 0.13 秒は UI を止めないための `setTimeout(0)` 34 回ぶんで、比較そのものは誤差 |

* **木全体の突き合わせは遅くない。** 1,718 項目で 0.17 秒。差分同期は「木がもっと
  大きくなったときに効く」対策であって、現状の支配項ではない（測って確かめた）。
* **2 秒より遅いときは、まず `watching` を見る**（上記）。次にサーバーの版を見る。
  v3.4.0 以前のサーバーには long-poll が無く、OS 側は 5 秒間隔のポーリングに落ちる。

## 変更履歴

* デーモン v3.7 — **無視するファイルを設定アプリから書けるようにした**（T-0059）。
  それまで `ignorePatterns` は仕組みだけがあり、`system/config/local_bridge.json` を手で編集するしかなく、
  事実として既定の 9 個のまま使われていた。あわせて**接続ごと・ルートごと**の指定を追加（全体の既定との和）。
  **無視は走査の入口で読み飛ばすだけなので、あとから足したパターンは既存のスタブに効かない。**
  そのため「無視対象のスタブを掃除」を追加した（`ignoreCleanup()`）。
  掃除が消すのは**スタブとアンカーの項目だけ**で、実体化済みのファイルとホスト側には触れない。
  調停と同時に走ると結果が黙って打ち消されるため、既存の直列化（`mount.syncing`）に相乗りしている。
* デーモン v3.6 — **設定アプリに「すべてスタブに戻す」を追加**（T-0037）。
  検証付きスタブ化を `releaseVerified()` に切り出し、`local_release` と設定アプリの
  両方がこの 1 つを通るようにした（判定を 2 か所に置かない）。あわせて 200 件ずつの
  分割と進捗の放送を追加。アプリ ⇄ デーモンは `local_bridge:request` /
  `:progress` / `:result` の放送でやり取りする。
  **`broadcast` は送信者自身にも届く**ので、`origin` で自分の放送を弾いている。
* v3.5.0 — **`/api/status` の long-poll 化**（PR #29 で取り込み。#28 は base の指定を誤って
  行き止まりのブランチへ入ったため出し直した）。`?wait=<秒>&since=<版>` で版が変わるまで応答を
  保留する。OS 側は 5 秒間隔のポーリングをやめ、返り次第すぐ次を投げる
  （実測: 通しで 3.3〜6.1 秒 → 約2秒。**ばらつきが 2.8 秒幅から 0.4 秒幅へ潰れた**。
  無変更時の往復も 6 回/30 秒 → 1 回/30 秒）。
  旧サーバーは `longPoll` を名乗らないので、その相手には従来の 5 秒間隔へ落ちる。
* v3.4.0 — **`attach` で追加したルートにも変更監視を張る**。それまでは起動時に在ったルートに
  しか監視が無く、あとから追加したルートは**60秒ごとの保険走査でしか気づかなかった**
  （実測: 書き込みから `rev` 更新まで 59.67 秒 → 1.56 秒）。
  あわせて `/api/status` の各ルートに `watching` / `watchError` を出す。
* v3.3.0 — ブロックするハンドラを素の `def` に（シェル実行中に全 API が停止していた）
* v3.2.0 — WebSocket を撤去し `rev` ポーリングへ（**ホスト側の変更が伝わっていなかった**）
* v3.1.0 — サーバーが同一性を名乗る。接続名の自動決定、同一性照合、detach 後始末
* v3.0.0 — 接続 × ルートの二段構造、シェル実行、検索、実体化／スタブ化
